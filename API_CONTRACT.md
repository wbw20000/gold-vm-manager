# Gold VM Manager API / UI contract

Independent local app, NOT the DSH UI. Python stdlib backend with static HTML/CSS/JS frontend; no CDN/runtime packages.
Base URL is same-origin on 127.0.0.1, planned port18765. UI gets auth token from location.hash `#token=...`; remove fragment with history.replaceState after reading and keep token in sessionStorage for reload. All /api calls except health require `Authorization: Bearer <token>`. Mutations POST application/json, same-origin Origin required (browser sends it). No secrets/credentials in API responses or console.

Success responses: `{ok:true,...fields}`. Error: `{ok:false,error:"Chinese message",code:"machine_code"}`, HTTP400/401/403/409/500.

GET /api/state:
```
{ok:true, app:{name:"Gold VM Manager",version:"1.0.0"},
 host:{cpu_count:10,memory_gib:64,free_disk_gib:180},
 vms:[{id:"gold",name:"gold",state:"stopped"|"running"|"suspended"|"missing",cpu:4,memory_gib:6,disk_gb:50,allocated_gb:31,
 network:{protected:true,blocked:false,management_enabled:false,normal_network:false},
 shares:[{id:"uuid",name:"project",path:"/absolute/host/path",read_only:false,enabled:true}],
 active_shares:[],pending_share_changes:false,pause_supported:true,
 busy:false,operation:null,last_error:null,last_event:null}],
 events:[{time:"ISO",vm:"gold",action:"start",message:"已请求启动",level:"info"}],
 capabilities:{native_picker:true}}
```
IDs come from the controller's current legacy mapping plus managed registry; the example names above are illustrative, not the complete allowed list. Shares are desired config; active_shares reflect last launch. stopped VM active_shares=[]; paused VM continues prior launch shares. Pending changes apply ONLY next cold start, not live/savedstate. Pause is unavailable while active shares or the generated setup share exist. network.blocked shows existing drop_proxy but UI MUST NOT add an unblock control or silently change it. allocated_gb is an allocation estimate; shared APFS extents mean it must not be summed as unique physical usage. The main panel does not display the former verbose disk-allocation paragraph.

POST /api/vms/<id>/action body `{action:"start"|"pause"|"shutdown"|"force-stop"|"discard-state"|"focus"|"finish-first-setup", confirm_name?:"gold"}` -> {ok:true,message:"..."}. start is asynchronous return202 and UI pollsstate. shutdown sends guest power-button request, may require macOS confirmation INSIDE guest; NOT guaranteed shutdown. force-stop and discard-state require modal + exact typedVMname; they can lose unsaved data. Never auto force/discard. `recovery-start` additionally requires the exact VM name, stopped state, and a compatible generated protected launcher; it preserves the network fence and mounts no shares. start while suspended resumes old directory config and pending updates wait for normal shutdown. pause supported only no active shared directories.

POST /api/vms/<id>/shares body `{shares:[{id?:"uuid",name:"project",path:"/host/path",read_only:false,enabled:true}]}` saves desired full list. Backend canonicalizes, validates user-owned existing directory, rejects dangerous roots/private keys/VM images/control files, colon or newline paths incompatible with Tart. Use default readonly false ONLY with explicit warning/consent at Add or access-mode change (checkbox client; backend `acknowledge_write:true` if any RW entries added/new path/changedRO->RW). Disabling/removing needs no destructive physical file action. Does NOT create or delete host dirs. Return {ok:true,shares:[...],pending_share_changes:bool,message:"..."}. No silent restart.

POST /api/pick-directory `{vm:"gold"}` -> {ok:true,path:"/canonical/path"} OR {ok:true,cancelled:true}. Native macOS choose-folder dialog opened ONLY by explicit click; optional manual path works too. Picker can remain pending; HTTPclient needs long timeout. Native picker foreground activation is user-triggered; no admin prompts.

POST /api/reveal-directory `{vm:"gold",share_id:"uuid"}` -> {ok:true} opens Finder for EXISTING configured share only. The manager does not offer a host Claude launch or command-copy action and does not read shared file contents.

### New disk size and offline expansion (1.6)

`disk_gib` on creation is a whole integer **30–1024** (default 50). In one-click preflight on one filesystem, allow disk + 12 GiB when reusing the cached, reviewed IPSW, otherwise disk + 32 GiB. With separate filesystems: disk + 2 GiB for VM storage and 10 / 30 GiB on the materials volume. Cache metadata is only a budgeting hint: image hashing and the native pre-create space check still run.

`GET /api/state` includes `disk_capacity_bytes` (apparent bytes, nullable) and `disk_growth_supported`. Host allocated blocks and free space inside the guest are different measurements. `POST /api/vms/<id>/expand-disk` accepts exactly `{target_gib:40,expected_bytes:32212254720,acknowledge_growth:true}` to grow a 30 GiB published managed macOS VM to 40 GiB **total**. It is authenticated and same-origin; only eligible, stopped VMs with their original bound environment and no busy/saved/attached/open disk can proceed. No shrink, resize-in-place of a running guest, partition repair, automatic retry, backup creation, mount or launch. Only report success on durable raw-size readback (`virtual_capacity_bytes`). Ambiguous completion requires refreshing and checking actual disk size before any new request. A larger virtual block device does not guarantee a larger APFS volume; see the [user guide](ONE_CLICK_PREINSTALL.md).

POST /api/vms/<id>/delete body `{confirm_name:"exact VM name",acknowledge_erase:true}` queues a dedicated deletion job. Requires the trusted inventory target to be stopped or suspended; it does not stop running VMs. Completion is reported through `build_job`, not inferred from HTTP success. Exact retention and journal semantics: [VM_DELETION.md](<VM_DELETION.md>).

POST /api/build accepts explicit create/rebuild requests, user-selected names/resources, acknowledged setup materials, and additional exact-name/erase confirmation for rebuild. `build_job` reports progress, terminal results, and recovery interlocks; incomplete journals must not be hidden. See [CREATE_REBUILD_GUIDE.md](<CREATE_REBUILD_GUIDE.md>) and current request validation in [manager.py](<manager.py>).

`POST /api/build` also accepts the **separate restore-only development mode** when `capabilities.offline_validate=true`:

```json
{"mode":"offline_validate","name":"fresh-test","cpu":2,"memory_gib":4,"disk_gib":50,"ipsw":"/absolute/trusted-local.ipsw","acknowledge_offline":true}
```

This mode rejects `source_vm`, `confirm_name`, `acknowledge_erase`, and `setup_profile`; it does not require legacy node-migration `acknowledge_setup`. No `latest` download is allowed. A local image's compatibility inspection is not independent provenance/digest verification. It restores into a new private stage, never calls legacy provisioning or commit, never publishes/boots a guest, and never marks applications installed. Successful restoration terminates at `awaiting_offline_preinstall`, with `system_restored:true`, `applications_preinstalled:false`, `desktop_verified:false`, `guest_started:false`, `credentials_copied:false`, and a private `stage_path`. The job remains visible without a VM startup link; HTTP 202 and restore success are not application/desktop acceptance. `guest_started` excludes the installer's internal virtualization and means no ordinary post-restore guest start.

This restore-only mode never installs applications. The full preinstall flow below does not write into the guest disk either (2026-11-20): it prepares a read-only installers folder instead. See [OFFLINE_PREINSTALL.md](<OFFLINE_PREINSTALL.md>) for source pins, signature/quarantine requirements and the folder.

### Full preinstallation (`preinstall`, separate from `/api/build`)

- `GET /api/preinstall/capabilities` returns `{ok,ready,checks,supported_tuples,applications,limitations,restore_image_cached}`. It does not download, start a VM, test VPN connectivity or grant OS authorization. `restore_image_cached` is a boolean hint that an accepted copy of the pinned restore image is already in the private cache (records, file identity and size only; nothing is hashed). It only shapes the dialog's wording: every build still hashes the whole image before using it.
- `GET /api/preinstall/examples` returns `{ok,yaml,fields}` with fixed, deliberately nonworking examples. There is no export endpoint for an uploaded profile.
- `POST /api/preinstall/vpn/validate` accepts exactly `{submission,allow_resolve}`. `submission` is `{input_mode:"fields",nodes:[...]}` or `{input_mode:"yaml_path",path:"/absolute/local.yaml"}`. The latter reads only an explicitly selected private-safe local file, with a 256 KiB limit, never returning or persisting the path or raw file. Legacy callers can still send `{input_mode:"yaml",yaml_text:"..."}` with the same parser limit; only this route has a larger wire limit for JSON escaping. A third form, `{input_mode:"vm",vm:"<name>"}`, reissues the configuration that one of the manager's own v3 VMs was built with: it is read back from that VM's private environment, accepted only if it still matches the digest and endpoint policy pinned when the VM was prepared, and reparsed without DNS; `allow_resolve` must be `false`, the source VM is only read (running or not), and the summary has no warnings because nothing is replaced. An unknown name, a VM without an installers folder (v2) and a changed file all get the same `vpn_validation_failed`. `allow_resolve` is a real boolean. Returns `{ok,configuration_id,summary,expires_in_seconds,configuration_stored_privately:true,vpn_connected:false}`. No secret, resolved address, filename, node name or config is returned. Node input is not accepted by the creation route.
- `POST /api/preinstall/create` accepts `name`, optional integer `cpu`, `memory_gib`, `disk_gib`, `ipsw` (`"reviewed"` or explicit absolute path to the same pinned restore image), `vpn_configuration_id`, optional `download_loopback_proxy` (`null` or credential-free `http://127.0.0.1:port`), and literal true `acknowledge_preinstall` and `acknowledge_network_policy` (the retired `acknowledge_guest_autoconfigure` is now an unknown key and refused). If the private validation record marks normalization required, it additionally requires `acknowledge_normalization:true`. It accepts no predecessor, arbitrary artifact URL, credential, or startup flag. Response HTTP 202 `{ok:true,job:{id,mode:"preinstall",name,phase:"queued",...}}` binds that ticket to one job. The UI sends these acknowledgements only when the user activates the explicit final consent button after the operation note and any normalization warnings. An implicit form submission does not start a job.
- Alternatively, `POST /api/preinstall/create` accepts `defer_vpn:true` plus the ordinary resource/image arguments and `acknowledge_preinstall:true`, without VPN ID or other VPN acknowledgements. The worker records `awaiting_vpn_configuration` after the isolated restore and application verification; the disk stays unpublished/unstarted. `POST /api/preinstall/resume` accepts exactly `job_id`, `vpn_configuration_id`, literal true `acknowledge_network_policy`, plus `acknowledge_normalization:true` if required. It returns 202 in `vpn_resume_queued` and verifies the exact paused checkpoint and retained materials before continuing on the same disk. New lifecycle jobs cannot replace the waiting task.
- `/api/state.build_job` shows phases including `acquiring`, `inspecting`, `installing`, `preparing_runtime` (building the installers folder and the protected environment), `publishing`, and `awaiting_first_desktop_acceptance`. There is no administrator-authorization phase any more. The reviewed IPSW digest and Apple inspection do different jobs: inspection plus the durable completion receipt must agree with 26.6.2 / 25G83, and the completion build is rechecked at publication. A started stage (saved state) is never published; the journal and live verification gate startup. Incomplete transactions remain locked. `vms[].preinstalled.installers_share` is true for a v3 VM (installers folder, nothing written into the guest) and false for an older v2 VM, whose `vms[].preinstalled` can show a bounded guest self-report; neither it nor network counters are an independent connectivity or desktop check.
- A failed preinstall `build_job` carries `failed_phase` and `failure_code`, such as `installer-copy-failed`, `installer-copy-mismatch` or `installer-quarantine-mismatch` while building the installers folder. Jobs recorded by older builds may also carry `failed_step` and `failure_reason`. All are constant slugs; native output, paths and node data are never included. The UI shows step, reason and raw codes.
- A preinstall `build_job` may carry `materials_source` (`"reused"` when this store's earlier completed application download passed full revalidation, `"downloaded"` otherwise). A material failure (`failed_phase: "acquiring"`) carries `failed_product` (`ccbaga`, `clashVergeRev` or `claudeDesktop`, when known) and a fixed cause in `failure_code`, such as `download-timeout`, `download-connection-lost`, `download-connect-failed`, `download-dns-failed`, `download-tls-failed`, `download-deadline-exceeded`, `truncated-download`, `checksum-mismatch` or `host-disk-full`; `<stage>-failed` means no fixed cause was available. During acquisition `message`/`progress` name the product and MiB downloaded.
- The administrator-authorization pause and `POST /api/preinstall/authorization` were removed with the guest ownership helper; that route now returns 404.
- `POST /api/preinstall/archive` accepts exactly `{job_id, confirm_name}` for the current preinstall job when it is `failed`/`interrupted`, unpublished, has no publication journal, no active inner operation and a detached stage disk, and the lifecycle lock is free. It moves only `build-current.json` to `build-jobs/<id>/archived-current.json` so a new fresh job can start; the stage under `~/.tart/.gold-manager-staging/<id>` is retained, not resumed, deleted, published or started. Rejections return 409 `archive_rejected`.
- Starting a published v2 or v3 VM requires separate `POST /api/vms/<id>/action` body `{action:"start",confirm_name:"<exact name>",acknowledge_reviewed_unsigned_backend:true}` while stopped. This permits the exact private backend copy's owner-execute bit and normal OS execution only. It is not a Gatekeeper exception, an OS consent, or native trust approval. Neither the worker nor connectivity reporting requests startup. No NAT fallback. The field name is historical: the backend is now gvproxy from Podman's installer, signed with Red Hat's Developer ID and notarized. For an environment prepared before 2026-11-19, the confirmed start first refreshes the private runtime to that backend and the current launcher code (it may download the ~77 MB installer); an intact signed environment only takes the current launcher code, without a download. A failure is reported as the VM's operation error `backend_refresh_failed` and no VM starts.
- **First setup uses Tart's normal network** (owner's decision, 2026-11-19). While `vms[].preinstalled.first_setup_pending` is true, the start body is `{action:"start",confirm_name:"<exact name>",first_setup_normal_network:true}` with no backend field; anything else returns 409 `first_setup_confirmation_required`. This run has no packet filter and runs no backend; the guest uses the host's network directly. A v3 VM also gets its installers folder as the read-only share `gold-installers` for this run only. `vms[].network.normal_network` is true while such a run is live. `{action:"finish-first-setup"}` (preinstalled VMs only, otherwise 409 `first_setup_unavailable`) records once, irreversibly, that every later start is the protected start above; it is synchronous, idempotent and, if the VM is running, takes effect after shutdown. Afterwards `first_setup_normal_network` returns 409 `first_setup_finished`. An unreadable or unexpected record returns 409 `invalid_network_mode` and nothing starts. `first_setup_normal_network` on any other action or VM returns 400 `invalid_execution_consent`.

`confirm_name` in action, delete and archive bodies binds the request to the VM or job the dialog was opened for. Since 2026-11-20 the UI fills it in itself: every confirmation is one click on the dialog's button, with no typed name. The server checks are unchanged.

See [the preinstall user guide](<ONE_CLICK_PREINSTALL.md>) for OS authorization and data retention. The API does not accept guest account passwords or provision login. The legacy first-boot account automation remains experimental and is not used by this path.

Optional GET /api/health is unauthenticated and returns app/version health without private paths. The state example above is abbreviated; current state also includes managed-VM setup/rebuild/recovery capabilities and build_job.

Visual language Chinese; light gray/white surfaces, black text, blue primary controls and clearly outlined red destructive controls. Main operation buttons have at least 44-point height; responsive cards, status chips and per-VM shared-folder list; native directory picker plus manual entry; clear share read-only/readwrite, guest mountpath `/Volumes/My Shared Files/<name>` and guest-only Claude workflow. Empty state deliberate. Show in-app confirmation dialogs, toast success/errors; avoid alert()/confirm() for main UX. Control busy + client async status polling every3s without overwriting edited form. No mock runtime data in production UI. Data rendered via textContent not unsafeHTML. CSPallows only self; no inline event handlers or externalfonts/scripts. Provide static/index.html, style.css, app.js only in delegated UI scope.
